# TAHFD Heartbeat Trace Dataset (Anonymous Review Version)

## Overview

This repository accompanies a manuscript submitted for anonymous peer review on a trust-aware hierarchical failure detection (TAHFD) approach. It provides **a small sample of heartbeat-trace data** to illustrate the data format and experimental setup. The underlying study evaluates the approach using (i) preprocessed real-world PlanetLab heartbeat traces and (ii) synthetically generated hierarchical heartbeat traces with controlled fault injection.

**Data availability:** The complete experimental dataset is approximately **11 GB** .

## 1. Real-world PlanetLab trace preparation

The source traces were recorded across **10 PlanetLab nodes** over approximately **150 hours**, with heartbeats transmitted every **100 ms** in the original mesh experiment. The trace records contain sender identifiers, sequence numbers, and transmission and reception timestamps.

For the hierarchical evaluation, the original observations were *reorganized*, not recollected under a new network topology:

1. Raw trace logs were converted into CSV files and partitioned into manageable chunks.
2. Monitoring streams were retained for **root node 9** and **parent nodes 5, 6, and 7**; other nodes were treated as monitored children (**0, 1, 2, 3, 4, and 8**).
3. Records were reorganized by monitored sender and monitoring receiver into per-link traces.
4. Nonessential fields were excluded while preserving node identifiers, sequence numbers, and original send/receive timestamps. Existing gaps, out-of-order records, and observed timing variability were not removed through random sampling.
5. Inter-arrival times can be computed from successive reception timestamps for detector evaluation.

The hierarchical roles are a **post-processing interpretation of existing mesh observations**. They do not imply that the original PlanetLab traffic was generated by a hierarchical network deployment.

## 2. Synthetic trace generation

Synthetic heartbeat streams were generated to assess failure detection at three system sizes under controlled conditions:

| Topology | Root nodes | Parent nodes | Child nodes | Parent–child monitoring links |
| --- | ---: | ---: | ---: | ---: |
| N10 | 1 | 3 | 6 | 18 |
| N50 | 1 | 7 | 42 | 126 |
| N100 | 1 | 9 | 90 | 270 |

Each child is assigned to **three parents** using balanced round-robin monitoring. The generated traces cover **72 hours** at a **100 ms heartbeat interval**. The generator uses **random seed 42**.

Link properties were informed by the statistical behavior of the original PlanetLab observations. In the reported generation procedure:

- Per-link inter-arrival variability is sampled from empirical stability classes.
- Per-link packet-loss probabilities are sampled from **0.04%–0.28%**.
- Base one-way delays are sampled from **5–150 ms**, with **20% multiplicative jitter**.
- In addition to independent losses, burst-loss events are modeled with a **0.2% trigger probability per heartbeat interval**, an average **5 s** burst duration, and an elevated **15%** loss rate during bursts.

The synthetic traces are **simulation-generated data**, not additional direct measurements from PlanetLab.

## 3. Controlled fault injection and ground truth

The synthetic experiments include controlled **crash, crash-recovery, timing, omission, and link** failure scenarios. A ground-truth JSON manifest in the complete archive specifies the affected node or link, fault type, injection start, and duration. These records support evaluation against known injected events.

The fault schedule varies by topology: in particular, the **N10 scenario does not include link-failure injections**, whereas the larger N50 and N100 configurations do. A small CSV sample cannot be assumed to contain every injected failure category. Ground-truth files are included in this repository only if explicitly uploaded.

## 4. Trace format

Heartbeat CSV records are organized by monitoring relationship in the complete archive. Their core fields have the following meanings (exact punctuation/spacing of headers may depend on the CSV export):

| Field | Description |
| --- | --- |
| `Node_ID` | Identifier of the monitored/sending node |
| `S_NUM` | Heartbeat sequence number |
| `Send_T(ms)` | Heartbeat transmission timestamp in milliseconds |
| `Rec_T(ms)` | Heartbeat reception timestamp in milliseconds |

The receiving monitor can be identified from the associated file or folder context. For a single flattened sample, this context must be stated in the file description or accompanying metadata.

Inter-arrival time at the receiver is calculated as `IAR[k] = Rec_T[k] - Rec_T[k-1]` after applying the relevant per-link ordering. Sequence-number gaps can indicate lost or omitted heartbeat observations. Timestamp differences between separate machines should **not** automatically be interpreted as synchronized one-way network delays.

## 6. Reproducibility and limitations

- The study's full evaluation uses both real preprocessed traces and larger synthetically generated traces; this repository contains only a subset.
- The original PlanetLab observations exhibit naturally occurring losses, jitter, and asymmetry; the synthetic traces are statistically informed approximations with explicitly injected events.
- Reproducing aggregate results requires the complete per-link traces, relevant ground-truth manifests, detector implementation, and experimental configuration.
- Sample selection, filename, source (`PlanetLab` or `N10`/`N50`/`N100`), and monitored link should be documented alongside any uploaded sample. A sample should not be described as a complete benchmark.
